  baseline migrations محلية أعيد بناؤها من schema. لذلك يمنع تشغيل `db push` على
  الإنتاج أو الفرع بلا مراجعة؛ سيحاول اعتبار نسخ قديمة migrations جديدة.

## بوابة الفرع المؤقت

1. تأكيد تكلفة الفرع، ثم إنشاؤه باسم واضح ومؤقت.
2. التأكد أن الفرع لا يحتوي بيانات الإنتاج ولا يستخدم أسرار الإنتاج الخارجية.
3. تطبيق المهاجرات الاثنتي عشرة أعلاه فقط، كل ملف كعملية migration مستقلة.
4. تشغيل ملفات `supabase/tests/database/` كاملة. كل ملف يبدأ transaction وينتهي
   بـrollback، ولا يترك fixtures.
5. تشغيل مستشاري الأمان والأداء، والتحقق من:
   - grants وRLS و`SECURITY DEFINER` و`search_path`؛
   - Realtime publication وStorage policies؛
   - عدم ظهور hashes أو عدادات API للمستخدمين؛
   - عدم ظهور claim token أو حالة إرسال Push الداخلية في REST أو Realtime؛
   - بقاء إشعارات الطلب وعروض الدلفري على قناة `push` واحترام مفاتيح
     `notifications_enabled` و`order_notifications` و`promo_notifications`؛
   - عدم وجود settlement بعد refund/reversal؛
   - توازن ledger والمحافظ وCOD.
6. نشر `api-v1` على الفرع مع `verify_jwt = false` ونشر `send-push` مع
   `verify_jwt = true`، ثم مقارنة الكود والإعداد مع المستودع.
7. تجربة fixtures كاملة: عميل → تاجر → سباق مندوبين → إثبات → تسليم → تسوية، ثم
   الإلغاء، الإرجاع الفعلي، رفض كل القطع، الاسترداد، COD الجزئي/الكامل، الشكوى،
   السحب، اعتماد الدلفري بنسخة قديمة، ومفتاح API بعد الحظر والتجاوز. شغّل استدعاءين
   متزامنين لـ`send-push` على fixture بلا جهاز حقيقي، وتأكد من محاولة قاعدة بيانات
   واحدة ومنع عبور حد الإرسال الخارجي مرتين. عطّل كل تفضيل بدوره وتأكد أن Push
   يتوقف بينما يبقى الإشعار داخل التطبيق قابلًا للقراءة.
8. حذف الفرع فور توثيق النتائج لإيقاف التكلفة.

## بوابة الإنتاج

1. أخذ نسخة احتياطية قابلة للاستعادة وتسجيل migration history وadvisors الحاليين.
2. إيقاف أي نشر واجهة متزامن، وتحديد نافذة مراقبة ومالك قرار rollback.
3. تطبيق المهاجرات الجديدة بالترتيب المحدد فقط؛ لا تستخدم `db push` العام قبل
   إصلاح اختلاف timestamps في migration history.
4. نشر Edge Functions بإعداد JWT المطابق لكل دالة.
5. تشغيل فحوص قراءة فقط بعد النشر: العقود، grants، RLS، Realtime، Storage، advisors،
   وأعداد حالات المصالحة، دون إنشاء طلبات حية.
6. معالجة الطلبين بلا tracking والطلب المسلّم غير المتسق من شاشة المصالحة وبأدلة،
   لا بتحديث SQL تخميني.
7. إبقاء مراقبة الأخطاء والـdeadlocks والـ5xx والتسوية المكررة فعالة طوال النافذة.

## الرجوع والإصلاح الأمامي

- لا تعتمد rollback SQL عكسيًا لجداول مالية أو أدلة عهدة بعد بدء حركة حية.
- قبل فتح الكتابة للمستخدمين، يمكن الاستعادة من النسخة الاحتياطية إذا فشلت migration.
- بعد بدء الحركة، استخدم forward-fix جديدًا ومراجعة يدوية للحالات المتأثرة؛ لا تحذف
  settlement أو ledger أو proof أو audit history.
- إذا فشل Edge وحده، أعد نشر آخر نسخة موثقة وإعداد JWT السابق، مع إبقاء schema الجديد
  إن كان متوافقًا، ثم أصلح Edge للأمام.
